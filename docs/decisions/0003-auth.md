# ADR-0003: Auth library with roles, shared by shoppers and admins

Status: **Library approach accepted; Better Auth proposed** · Date: 2026-10-31

## Context
Shoppers sign in with Google or with email and password, only when they check out. One admin now, more later. Writing authentication ourselves (password hashing, sessions, reset tokens, rate limiting) is easy to get subtly wrong.

## Decision
- Use an auth library that stores users and sessions in **our own Postgres**. Proposed: **Better Auth** (email-and-password, Google, database sessions, built-in rate limiting).
- One `user` table with a `role` column (`customer` | `admin`), checked on the server by `requireAdmin()` in every admin action.
- **Database sessions** rather than stateless tokens, so sessions can be revoked when admin rights are removed.
- No public admin sign-up: the first admin comes from a script; later admins are granted by an existing admin.
- Email delivery (verification, reset) via a provider; proposed **Resend**.

## Alternatives considered
- **Auth.js (NextAuth):** widely used, but its email-and-password support is limited and discouraged by its own docs.
- **Hosted auth (Clerk, etc.):** fastest to set up, but user data lives with a third party and costs grow with users.
- **Build it ourselves:** most control, highest security risk and effort.

## Consequences
- Pros: we own user data; one login system for everyone; adding admins is a data change, not a redesign.
- Cons: a new dependency plus an email provider; we must keep the library up to date for security fixes.

## Revisit when
Admins need two-factor login (add it via the library), finer-grained roles are needed, or phone/OTP sign-in is requested.
